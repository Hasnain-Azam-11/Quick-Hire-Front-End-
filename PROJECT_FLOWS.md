## 1. Overview

### What the App Does
QuickHire is a two-sided marketplace for hiring local service workers in Pakistan (drivers, cleaners, caregivers, handymen, event staff, cooks, tutors, etc.), priced in PKR across 8 Pakistani cities (`src/constants/categories.js`).

There are two hiring paths:
1. **Job Posting Flow**: A client posts a job request (`POST /Client/jobs/`) → workers browse open jobs and apply → the client reviews applicants and accepts one → a booking is created.
2. **Direct Hire ("Offer" / "Hire Request") Flow**: A client browses public worker service listings (`GET /worker/browseworkers/`), opens a worker profile or card, and sends a direct hire offer → the worker accepts or declines → if accepted, a booking is created.

Once a booking is created, the UI supports a mock checkout/payment flow (JazzCash, EasyPaisa, Card), client-to-worker reviews, 1-on-1 messaging, notifications, and an admin portal for worker CNIC verification.

## 3. Flows

> [!IMPORTANT]
> **Real vs. Mock Boundary**:
> - **REAL (wired to Django backend)**: Registration (`POST /Client/registration/`), Login (`POST /api-token-auth/`), Current User Profile (`GET`/`PATCH /Client/me/`), Job Creation & Listing (`GET`/`POST /Client/jobs/`), Worker Bio (`POST`/`GET`/`PATCH /worker/workerBio/`), Worker Services (`GET`/`POST /worker/workerService/`), and Public Worker Listing (`GET /worker/browseworkers/`).
> - **MOCK (browser `localStorage` only via `MarketplaceContext.jsx`)**: Job Applications, Accepting Applicants, Direct Hire Offers, Bookings/Schedule, Payments/Checkout, Reviews, Chat Conversations/Messages, Notifications, Duty Toggle, and Admin Verifications.
> - Because mock data lives in `localStorage` (`quickhire_market_v1`), actions in the MOCK flows only appear to the "other user" if both users sign in on the **same browser** (or once the backend implements the corresponding endpoints).

> **Note on `jobToApi` Encoding (`src/api/jobs.js`, lines 16–71)**:
> Because the backend `JobPost` model has no `title`, `services`, or `price_unit` columns:
> - `job_description` is encoded as `"Title: <title>\nServices: <s1, s2>\n\n<description>"` (omitting `Title:` or `Services:` if empty).
> - `duration` is encoded as `"Permanent"`, `"Event"`, `"Task"`, `"Session"`, or `"<N> <hour|day|week|month|year>(s)"`.
> - `category` is mapped from label (`"Event Staffing"`) to backend slug (`"event_staffing"`) via `toBackendCategory()` (`src/api/categories.js`).

## 6. Missing, Broken, or Unclear in the Frontend

### 6.1 ID Mismatches Between Real Backend Entities and Local Mock Entities
1. **Direct Hire (`createOffer`) silently fails for real backend workers**:
   - On `/workers` and `/worker-profile/:id`, `worker` comes from `GET /worker/browseworkers/` (`publicWorkers`), where `worker.id` is the numeric `WorkerService.id` (`src/api/worker.js`, line 92).
   - When the client submits `HireModal`, it calls `createOffer(worker.id, form)` (`src/components/HireModal.jsx`, line 46).
   - `createOffer` looks up `db.workers.find((w) => w.id === workerId)` (`src/context/MarketplaceContext.jsx`, line 416). However, `db.workers` only contains the 12 seed workers (`'demo-worker'`, `'seed-w2'`, ...) and workers created in this browser keyed by `user.id` (**username**). It does not contain numeric `WorkerService.id`s, so `target` is `undefined` and `createOffer` returns `null` without creating an offer, while `HireModal` still displays `"Hire Request Sent!"`.
2. **Messaging a real worker from `WorkerProfile` uses a synthetic ID that never matches the worker's session**:
   - `workerFromApi()` sets `userId: "worker-" + api.worker` (`src/api/worker.js`, line 94).
   - Clicking "Message" on `WorkerProfile.jsx` (line 55) starts a conversation with `"worker-<workerBioId>"`.
   - When that worker signs in, their `meId` is `user.id` (their **username**, `src/context/AuthContext.jsx`, line 130), so they never see the conversation or notification.
3. **"View public profile" / "View public listing" links use `user.id` (username) instead of `WorkerService.id`**:
   - `src/pages/worker/WorkerHome.jsx` (line 584), `src/pages/Profile.jsx` (line 128), and `src/components/layout/WorkerTopNav.jsx` (line 174) link to `/worker-profile/${user?.id}`.
   - `WorkerProfile.jsx` (line 21) looks up `getWorker(id)` in `publicWorkers` by `WorkerService.id`, resulting in `"Worker Not Found"`.
4. **Inconsistent casing of `worker_bio_id` on the backend**:
   - `POST /api-token-auth/` returns `worker_Bio_id` (capital `B`), whereas `GET /Client/me/` returns `worker_bio_id` (lowercase `b`) (`src/api/auth.js`, lines 25–31; `src/api/profile.js`, line 35). The frontend currently checks both.
5. **Multiple services per worker vs. single worker identity**:
   - `GET /worker/browseworkers/` returns one item per `WorkerService` (`src/api/worker.js`, lines 12–13). A worker with 3 services appears as 3 cards with 3 different `:id`s on `/workers`. It is not yet defined whether offers, bookings, and reviews should foreign-key to `WorkerBio` or `WorkerService`.

### 6.2 Missing UI / Unreachable States
1. **No way to mark a Job or Booking as Completed or Cancelled**:
   - `BookingDetail.jsx` (lines 13–25) defines styles for `pending`, `confirmed`, `completed`, and `cancelled`, and `MyRequests.jsx` (lines 206–216) shows a `"Leave a Review"` button only when `job.status === 'Completed'`.
   - Neither client nor worker has any button to mark a job or booking as completed or cancelled.
2. **Workers cannot view `/bookings/:id`**:
   - `BookingDetail.jsx` (line 35) checks `if (!booking || booking.clientId !== user?.id)` and shows `"Booking Not Found"`.
   - Yet `payForBooking()` (`src/context/MarketplaceContext.jsx`, line 666) sends the worker a notification linking to `/bookings/${bookingId}`, and `PaymentHistory.jsx` (line 14) links every row in the worker's `"What I Received"` tab to `/bookings/${booking.id}`.
3. **Job-based bookings have no link to `/bookings/:id` or `/checkout/:bookingId` from `/my-requests`**:
   - On `/my-requests`, `"Accepted, view booking"` and `"Pay Now"` only render under the `"Hire Requests"` (`offers`) tab (`src/pages/MyRequests.jsx`, lines 121–138). For a booking created by accepting a job applicant (`source: 'job'`), the client can only reach it via `/payments`.
4. **No edit or delete UI for Worker Services**:
   - `updateWorkerService` (`PATCH /worker/workerService/<id>/`) is defined in `src/api/worker.js` (lines 134–144) but never imported or called. There is no delete function or UI on `/worker/services` (`src/pages/worker/WorkerServices.jsx`).
5. **Client profile (`/profile`) is read-only & has no picture upload**:
   - `Profile.jsx` has no edit form. `PATCH /Client/me/` is only called from `/worker/settings` (`WorkerSettings.jsx`, line 45), so a client who is not a worker cannot edit their name or phone number.
   - Neither clients nor workers have a UI to upload `profile_picture` / `worker_picture`.
   - In `WorkerSettings.jsx` (line 123) and `WorkerProfileFields.jsx` (lines 124–153), selecting a CNIC image only saves `cnicFile.name` as a string in `localStorage` (`src/utils/workerProfile.js`, line 34); the file itself is never uploaded.
6. **Hardcoded / Dead UI Elements**:
   - `GoogleButton.jsx` (`"Sign in with Google"` / `"Sign up with Google"`) has `type="button"` and no `onClick` handler (`src/components/ui/GoogleButton.jsx`).
   - `"Forgot password?"` on `/sign-in` links back to `/sign-in` (`src/pages/SignIn.jsx`, line 106).
   - Landing page search (`Hero.jsx`, line 34), `PopularServices.jsx` (line 87), and `GetHelpTaskMatrix.jsx` (line 31) navigate to `/register?q=...` or `/register?category=...`, but `Register.jsx` never reads `q` or `category` from `searchParams`.
   - `WorkerReviews.jsx` (lines 10, 27–49) hardcodes `avgRating = 4.9` and the 5-star/4-star/3-star percentage bars (`90%`, `10%`, `0%`) instead of computing them from `reviews`.

- **Permissions and filtering on `GET /Client/jobs/` and `GET /worker/workerService/`**: The frontend assumes both endpoints return **all** records across all users and filters them in the browser (`isMine` in `src/api/jobs.js` line 78; `s.worker === workerBioId` in `src/api/worker.js` line 131).
